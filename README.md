# Ποδηλασία στα Ιωάννινα — τεκμηρίωση λειτουργίας (07/11/2026)

## Απλή πλοήγηση με προσωπικό προφίλ (18/11/2026)

- Η κάτω καρτέλα **Προφίλ** αντικατέστησε τη σκέτη καρτέλα «Μέλη». Χωρίς σύνδεση δείχνει μόνο επιλογές «Σύνδεση», «Νέα εγγραφή» και «Δες τα μέλη της ομάδας».
- Με έγκυρη προσωπική σύνδεση, το **Προφίλ** εμφανίζει φωτογραφία, συμμετοχές/χιλιόμετρα και τέσσερις καθαρές ενέργειες: **Πληροφορίες ποδηλάτου**, **Προγραμματισμένοι έλεγχοι**, **Νέο σέρβις**, **Παλιά σέρβις**. Η δημόσια λίστα μελών παραμένει προσβάσιμη με ξεχωριστό κουμπί.
- Η αλλαγή φωτογραφίας, η αλλαγή προσωπικού κωδικού και η αποσύνδεση μεταφέρθηκαν μέσα στο αναδιπλούμενο τμήμα **«Ρυθμίσεις προφίλ»**. Όλες οι λειτουργίες παραμένουν διαθέσιμες.
- Οι γενικές **Ρυθμίσεις** περιέχουν χρώματα, ειδοποιήσεις και Admin, όχι διπλό μενού σέρβις. Για συνδεδεμένο Admin, οι συχνές επιλογές **Νέα βόλτα** και **Ποδηλάτες & επισκέπτες** φαίνονται αμέσως. Διαδρομές/στατιστικά και ασφάλεια/Backup/Keep Alive ανοίγουν με αναδιπλούμενα τμήματα, χωρίς απώλεια δικαιωμάτων ή λειτουργιών.
- Δεν έγιναν αλλαγές στη βάση δεδομένων, στα Edge Functions, στα αποθηκευμένα ποδήλατα/σέρβις ή στους προσωπικούς κωδικούς στο πλαίσιο της **απλοποίησης πλοήγησης**.
- Σημείο επαναφοράς πριν τις αλλαγές: `backup/pre-profile-navigation-simplify-2026-11-18`.

## Προσωπικά προφίλ μελών (18/11/2026)

- Στην καρτέλα **Μέλη** εμφανίζονται τα κουμπιά **Εγγραφή νέου μέλους** και **Σύνδεση**. Κάθε νέο μέλος επιλέγει όνομα ή ψευδώνυμο (2–70 χαρακτήρες) και προσωπικό κωδικό (6–64 χαρακτήρες). Δεν απαιτείται email ή Supabase Auth λογαριασμός.
- Τα ήδη υπάρχοντα μέλη **δεν μπορούν να δεσμευτούν από άλλο πρόσωπο** μέσω αυτοεγγραφής: το όνομα/ψευδώνυμο πρέπει να είναι μοναδικό ανεξάρτητα από πεζά/κεφαλαία. Για κάθε παλιό μέλος, ο Admin ανοίγει **Ρυθμίσεις → Διαχείριση Admin → Ποδηλάτες & επισκέπτες → Ορισμός πρώτου κωδικού** και δίνει τον αρχικό κωδικό ιδιωτικά.
- Κάθε σύνδεση δημιουργεί ένα τυχαίο session token 60 ημερών αποθηκευμένο **μόνο στη συσκευή**. Στο Supabase αποθηκεύεται μόνο το SHA-256 hash του token· ο κωδικός μέλους αποθηκεύεται ως salted PBKDF2-SHA256 (210.000 επαναλήψεις). Υπάρχει περιορισμός αποτυχημένων προσπαθειών (7/15 λεπτά ανά όνομα), αλλαγή κωδικού από το μέλος όταν γνωρίζει τον παλιό και επαναφορά με **μία ωριαία έγκριση Admin**, μοναδικό κωδικό μιας χρήσης και ανάκληση παλιών συνεδριών.
- Η νέα Edge Function **member-accounts** χειρίζεται εγγραφή, σύνδεση, έλεγχο συνεδρίας, αλλαγή κωδικού και προσωπικής φωτογραφίας, καθώς και έγκριση/κατανάλωση κωδικού επαναφοράς. Οι υπάρχουσες **rapid-responder** και **bike-services** ελέγχουν πλέον το member token για δηλώσεις συμμετοχής στο όνομα εγγεγραμμένου μέλους και για **όλες** τις μεταβολές στα ποδήλατα/σέρβις αντίστοιχα. Η δημόσια ανάγνωση κατάστασης/στατιστικών παραμένει όπως ήταν.
- Ονομαστική επιλογή μέλους σε localStorage δεν αποδεικνύει ταυτότητα και δεν μπορεί πια να εξουσιοδοτεί τροποποιήσεις.
- Οι πίνακες `voltes_member_credentials`, `voltes_member_sessions`, `voltes_member_login_attempts` και `voltes_member_password_resets` έχουν RLS και **καμία** άδεια πρόσβασης από `anon`/`authenticated`. Η εγγραφή νέου μέλους γίνεται ατομικά από το RPC `voltes_member_register`, προσβάσιμο μόνο από `service_role`.
- **Τα υπάρχοντα ποδήλατα, οι βόλτες, τα σέρβις, τα χιλιόμετρα και το Admin PIN δεν άλλαξαν.** Αν κάποιο υπάρχον μέλος δεν έχει ακόμη κωδικό, χρειάζεται ο Admin να τον ορίσει πριν επεξεργαστεί σέρβις ή δηλώσει συμμετοχή με το κατοχυρωμένο όνομά του.
- Ο μηχανισμός Backup/Restore για βόλτες, μέλη και ποδήλατα **δεν εξάγει κωδικούς και συνεδρίες**. Σε επαναφορά σε νέα βάση, ο Admin ορίζει εκ νέου κωδικό στα παλιά μέλη.
- Δεν υπάρχει επιβεβαίωση πραγματικής ταυτότητας χωρίς email ή άλλη ανεξάρτητη απόδειξη. Ο κωδικός προστατεύει το προφίλ με το συγκεκριμένο ψευδώνυμο, όχι το φυσικό πρόσωπο πίσω από αυτό.


### Επαναφορά ξεχασμένου κωδικού — 1 ώρα

1. Ο Admin ανοίγει **Ρυθμίσεις → Διαχείριση Admin → Ποδηλάτες & επισκέπτες**, επιλέγει το μέλος με ενεργοποιημένο κωδικό και πατά **Έγκριση αλλαγής κωδικού · 1 ώρα**.
2. Εμφανίζεται **μόνο στον Admin** ένας τυχαίος κωδικός 20 χαρακτήρων χωρισμένος σε τέσσερις ομάδες, που μπορεί να αντιγράψει και να δώσει ιδιωτικά στο μέλος. Δεν αποθηκεύεται σε απλή μορφή στη βάση, ούτε στέλνεται αυτόματα.
3. Το μέλος πατά **Μέλη → Σύνδεση → Έχω κωδικό επαναφοράς**, συμπληρώνει όνομα, προσωρινό κωδικό και **νέο** προσωπικό κωδικό.
4. Η έγκριση **λήγει σε 60 λεπτά**, ακυρώνεται αμέσως μετά την πρώτη επιτυχημένη χρήση και αντικαθίσταται αν ο Admin εκδώσει νέο προσωρινό κωδικό. Η SQL συνάρτηση `voltes_member_consume_password_reset` καταναλώνει τον κωδικό, αντικαθιστά τον προσωπικό κωδικό και ανακαλεί παλιές συνεδρίες **ατομικά**.
5. Αν το μέλος **γνωρίζει τον παλιό κωδικό του**, τον αλλάζει από **Το προφίλ μου → Αλλαγή προσωπικού κωδικού** χωρίς αίτημα Admin. Αλλαγή με παλιό κωδικό ακυρώνει τυχόν εκκρεμείς εγκρίσεις επαναφοράς.
6. Ο Admin μπορεί να **ορίσει πρώτο κωδικό μόνο σε προϋπάρχον μη ενεργοποιημένο μέλος**. Δεν μπορεί πλέον να παρακάμψει τη διαδικασία επαναφοράς και να αντικαταστήσει απευθείας τον κωδικό ενός ήδη ενεργοποιημένου λογαριασμού.

**Ασφάλεια:** Χωρίς email δεν υπάρχει αυτόματη επιβεβαίωση πραγματικής ταυτότητας· ο Admin πρέπει να δίνει τον προσωρινό κωδικό στο σωστό άτομο εκτός εφαρμογής. Ο κωδικός επαναφοράς εμφανίζεται μόνο μία φορά στον Admin και χάνεται αν κλείσει η σελίδα· μπορεί πάντοτε να εκδώσει νέο. Δεν χρησιμοποιούνται PIN του Admin ή υφιστάμενα στοιχεία ποδηλάτου για επαναφορά.



## Τρέχουσα αρχιτεκτονική

- Στατικό PWA (GitHub Pages): `index.html`, `app.js`, `style.css`, `sw.js`, `manifest.webmanifest`.
- Supabase Postgres ως μόνιμη αποθήκη, με Edge Functions:
  - `supabase/functions/rapid-responder/index.ts`: βόλτες, μέλη, συμμετοχές, προβλέψεις, καιρός, είσοδος Admin.
  - `supabase/functions/bike-services/index.ts`: ποδήλατα και ιστορικό σέρβις ανά επιλεγμένο μέλος.
  - `supabase/functions/member-accounts/index.ts`: προσωπικοί κωδικοί, συνεδρίες, έγκριση και επαναφορά σε 1 ώρα.
- Το `config.js` ορίζει τη διεύθυνση της πρώτης Edge Function· η δεύτερη παράγεται από το ίδιο project URL.
- Όλες οι αλλαγές της βάσης διατηρούνται στο `supabase/migrations/`. **Μην επαναφέρετε παλιότερο snapshot της Edge Function από το GitHub**: ελέγχετε ότι είναι η τελευταία έκδοση πριν από deployment.

## Πληροφορίες ποδηλάτου (15/11/2026)

Στις **Ρυθμίσεις → Σέρβις ποδηλάτων → Πληροφορίες ποδηλάτου** κάθε μέλος βλέπει το/τα ποδήλατά του, τις αποθηκευμένες πιέσεις **μπροστά και πίσω σε bar και PSI** και τον κατάλογο εξαρτημάτων. Η «Επεξεργασία πληροφοριών» επιτρέπει τη διόρθωση 17 προαιρετικών κατηγοριών και των πιέσεων ανά ποδήλατο. Τα δεδομένα συγχρονίζονται από το υπάρχον endpoint `bike-services` στο Supabase (`voltes_bikes.bike_details` jsonb), χωρίς ξεχωριστό λογαριασμό ή επιπλέον χρέωση hosting. Κανένα υπάρχον σέρβις ή προγραμματισμένος έλεγχος δεν μεταβάλλεται.

**Ασφάλεια ελαστικών:** Οι πιέσεις είναι τιμές καταχωρισμένες από το μέλος, όχι υπολογισμένες εγγυημένες προδιαγραφές. Πριν τη χρήση ελέγχονται οι ενδείξεις ελαστικού και ζάντας (ιδίως για tubeless/hookless), το πραγματικό πλάτος και το βάρος αναβάτη.

## Δεδομένα και πρόσβαση

- Ο επισκέπτης βλέπει δημόσιες βόλτες και την κοινή λίστα μελών, ενώ τα λεπτομερή στοιχεία διαδρομών προορίζονται για Admin.
- Η επιλογή μέλους ανά συσκευή **δεν είναι σύνδεση/ταυτοποίηση**. Τα σέρβις φιλτράρονται βάσει ονόματος και ο χρήστης μπορεί να αλλάξει μέλος. Δεν προορίζονται για ευαίσθητα/απόρρητα δεδομένα.
- Τα νέα σέρβις αποθηκεύονται στο Supabase. Παλιά τοπικά στοιχεία εισάγονται μία φορά με έλεγχο διπλοεγγραφών. Οι διαγραφές αφήνουν μικρό δείκτη (`deleted_at`) ώστε άλλες συσκευές να μη δημιουργούν ξανά το σβησμένο ιστορικό.
- Δεν επιτρέπεται να διαγραφεί μέλος που έχει καταχωρισμένα ποδήλατα: διαφορετικά θα χάνονταν και τα σέρβις.
- Η είσοδος Admin χρησιμοποιεί τετραψήφιο PIN μόνο στο `login`, περιορισμό αποτυχημένων προσπαθειών ανά κλειδί σύνδεσης και στη συνέχεια αποθηκευμένο τυχαίο token. Τα απευθείας αιτήματα PIN σε άλλες Admin ενέργειες δεν επιτρέπονται.
- Μην αποθηκεύετε ποτέ `SUPABASE_SERVICE_ROLE_KEY` ή `ADMIN_PIN` στα δημόσια αρχεία του repository, στο `config.js` ή στον browser.

## Έλεγχοι πριν από κάθε αλλαγή

Το GitHub Actions workflow `.github/workflows/regression.yml` εκτελεί αυτόματα:

1. Έλεγχο σύνταξης όλων των αρχείων JavaScript της εφαρμογής.
2. `node tests/regression.cjs`: κουμπιά, αλλαγή μέλους, ιστορικό, XSS escaping, PWA cache και περιττά αιτήματα.
3. `npm test`: φόρμες διαδρομών, καταχωρίσεις, Admin, συμμετοχές, ιδιωτικά στοιχεία, ιστορικό.
4. `npm run test:db`: SQL migrations, RLS, δικαιώματα και ατομικότητα πράξεων σε PostgreSQL emulator.
5. `node tests/longterm-db.cjs`: αποτροπή απώλειας σέρβις, tombstones και φραγή αποτυχημένων PIN.

Για να τρέξουν τοπικά: Node.js 22+, `npm install`, `npm test`, `node tests/regression.cjs`, `npm run test:db`, `node tests/longterm-db.cjs`.

## Ανθεκτικότητα για πολλά χρόνια

- **Δεν είναι εφικτή εγγύηση 10 ετών χωρίς έλεγχο ή συντήρηση**: browser APIs, υπηρεσίες hosting και δωρεάν quotas αλλάζουν.
- Οι βόλτες και τα σέρβις δεν πρέπει να βασίζονται αποκλειστικά στο localStorage. Το PostgreSQL project είναι η πηγή αλήθειας.
- Διατηρήστε **ιδιωτικό, κρυπτογραφημένο αντίγραφο ασφαλείας της βάσης** εκτός του δημόσιου GitHub. Το GitHub αποθηκεύει κώδικα και migrations, **όχι** τα τρέχοντα δεδομένα του Supabase.
- Ελέγξτε περιοδικά ότι οι GitHub Actions είναι πράσινες, το Supabase project ενεργό και τα quotas εντός ορίου. Δωρεάν project μπορεί να παύσει μετά από παρατεταμένη αδράνεια.
- Οι υπηρεσίες τρίτων (Open-Meteo, OCR μέσω jsDelivr) είναι προαιρετικές. Τα βασικά δεδομένα καταχωρίζονται και χωρίς OCR ή πρόγνωση.
- Αν αλλάξει το endpoint, ενημερώστε το `config.js` και ανανεώστε την έκδοση του `sw.js` και των script URL στο `index.html` ώστε οι εγκατεστημένες PWA να πάρουν τη νέα έκδοση.
- Για πλήρη επαναφορά: ιδιωτικό backup δεδομένων, εφαρμογή migrations με τη σωστή σειρά, διαμόρφωση μυστικών στο Supabase, επανεγκατάσταση και των δύο Edge Functions και τέλος επανέκδοση του στατικού PWA.

### Έκδοση 0.5 — μέλη και κινητό

- Avatar Admin: φωτογραφίες JPG/PNG/WebP μικραίνουν και κόβονται κεντρικά σε JPEG 192×192. Αποθηκεύονται ιδιωτικά στο voltes_riders.avatar_data_url (έως 90.000 χαρακτήρες), χωρίς δημόσιο bucket. Υπάρχει αλλαγή/αφαίρεση και αρχικά ως εναλλακτική.

# Ποδηλασία στα Ιωάννινα — 0.4

Ενημέρωση του frontend από το GitHub snapshot 9c65d1d και της Edge Function που δόθηκε στη συνομιλία. Το backend δημοσιεύτηκε στο Supabase στις 31/10/2026 ως rapid-responder v2, μαζί με τη migration ride_completion_v2. Το frontend περιλαμβάνει όλες τις προγραμματισμένες βόλτες και τις 5 πιο πρόσφατες ολοκληρωμένες, χωρίς διαγραφή παλιών δεδομένων.

## Τι προστέθηκε

- Χειροκίνητη υψομετρική ανάβαση (0–50.000 ακέραια μέτρα).
- Χρόνος κίνησης Ω:ΛΛ, χωρίς στάσεις (π.χ. 1:40 → 100 λεπτά). Μέχρι 999:59, χωρίς τεχνητό περιορισμό 24 ωρών.
- Επιβεβαίωση των πραγματικών συμμετεχόντων: οι δηλώσεις συμμετοχής είναι προεπιλογές και μπορούν να αποεπιλεγούν. Τουλάχιστον ένας συμμετέχων απαιτείται.
- Οι επιλογές «δυσκολεύτηκε» αφορούν μόνο πραγματικούς συμμετέχοντες. Προαιρετικό ιδιωτικό σχόλιο Admin έως 2.000 χαρακτήρες.
- Διατηρούνται απόσταση, κοινή μέση ταχύτητα, Strava, PIN, δηλώσεις, μητρώο, μέλη/επισκέπτες, ιστορικό, διαγραφή και PWA, με το ίδιο μαύρο/πράσινο CSS.
- Τα νέα μεγέθη εμφανίζονται στο ιστορικό και αθροίζονται στα στατιστικά των πραγματικών συμμετεχόντων. Παλιά αρχεία με άγνωστα μεγέθη δείχνουν «—».

## Άμεση δοκιμή χωρίς πραγματικά δεδομένα

Με εγκατεστημένο Node.js 22 ή νεότερο, από αυτόν τον φάκελο:

    npm run preview

Άνοιξε http://127.0.0.1:8765. Menu → Είσοδος Admin → δοκιμαστικό PIN **1234**. Ολοκλήρωσε τη δοκιμαστική βόλτα με 35 km, 21 km/h, 120 m, 1:40, τον δοκιμαστικό συμμετέχοντα και ένα σχόλιο. Έλεγξε το ιστορικό, τα στατιστικά και αποσυνδέσου για να διαπιστώσεις ότι τα ιδιωτικά στοιχεία κρύβονται.

Το demo χρησιμοποιεί προσωρινά δεδομένα στη μνήμη, αντικαθιστά το config.js μόνο κατά την εξυπηρέτησή του και δεν συνδέεται στο Supabase. Επανεκκίνηση του server επαναφέρει τη βόλτα. Δεν προσομοιώνει όλες τις λειτουργίες του backend και δεν αντικαθιστά τη δοκιμή σε staging. Τερματισμός με Ctrl+C.

## Δοκιμαστική εγκατάσταση στο Supabase

1. Δημιούργησε δοκιμαστικό αντίγραφο της υπάρχουσας βάσης, μαζί με τους υπάρχοντες πίνακες, περιορισμούς και κατάλληλα δοκιμαστικά δεδομένα. Πάρε αντίγραφο ασφαλείας και κράτησε τον προηγούμενο κώδικα Function/frontend πριν από οποιαδήποτε παραγωγική ενημέρωση.
2. Εφάρμοσε τη migration **supabase/migrations/202610310001_completion_details.sql** στο δοκιμαστικό project. Είναι μία συναλλαγή. Προϋποθέτει τους υφιστάμενους πίνακες voltes_rides, voltes_riders και voltes_signups που χρησιμοποιεί ο παλιός κώδικας. Δεν αποτελεί bootstrap κενής βάσης. Μην την εκτελέσεις ξανά αν έχει ήδη εφαρμοστεί.
3. Διατήρησε το υπάρχον ADMIN_PIN μόνο στα secrets του δοκιμαστικού project. Το SUPABASE_URL και SUPABASE_SERVICE_ROLE_KEY παρέχονται από το Supabase runtime. Κανένα secret δεν μπαίνει στο config.js.
4. Ανάπτυξε τη Function από το **supabase/functions/rapid-responder/index.ts**, μαζί με το **supabase/functions/_shared/completion.js**, με Supabase CLI στο δοκιμαστικό project:

       supabase functions deploy rapid-responder --project-ref YOUR_STAGING_PROJECT_REF

   Το supabase/config.toml διατηρεί το υφιστάμενο συμβόλαιο: ανώνυμες δηλώσεις και server-side PIN για τις ενέργειες Admin. Δεν εισάγει login μέσω Supabase Auth. Το όνομα του endpoint είναι rapid-responder, ανεξάρτητα από την ετικέτα voltes-api στο Dashboard.
5. Σε δοκιμαστικό αντίγραφο του frontend άλλαξε το config.js ώστε να δείχνει στο /functions/v1/rapid-responder του staging. Το παρεχόμενο config.js διατηρεί το υπάρχον URL του project και δεν πρέπει να χρησιμοποιηθεί για δοκιμαστικές εγγραφές στο live.
6. Σέρβιρε τα αρχεία του frontend μέσω localhost ή HTTPS και δοκίμασε την πλήρη ροή: νέα βόλτα, δήλωση από δεύτερο browser, ολοκλήρωση με διαφορετικούς πραγματικούς συμμετέχοντες, ιστορικό, στατιστικά, αποσύνδεση, διαγραφή και ανανέωση δεύτερης συσκευής. Δοκίμασε 0 m, λάθος χρόνο 1:60, καμία συμμετοχή, παρατήρηση για μη συμμετέχοντα και επαναλαμβανόμενη ολοκλήρωση.
7. Έλεγξε από ανώνυμο αίτημα state ότι δεν επιστρέφονται ονόματα, slowed ή slowdownNotes. Ο νέος πίνακας ιδιωτικών σχολίων έχει RLS και πρόσβαση μόνο από service_role. Η migration αφαιρεί επίσης την απευθείας πρόσβαση anon/authenticated στους υπάρχοντες πίνακες: όλες οι λειτουργίες αυτής της εφαρμογής ήδη περνούν από την Edge Function.

Η δημοσίευση στην παραγωγή πρέπει να ακολουθήσει επιτυχή staging δοκιμή: migration → Function → frontend. Το νέο frontend απαιτεί capabilities.rideCompletionV2=true πριν επιτρέψει ολοκλήρωση, ώστε το παλιό backend να μην αγνοήσει σιωπηλά τα νέα πεδία. Οι υπόλοιπες λειτουργίες συνεχίζουν με το παλιό API. Η απευθείας χρήση παλιού frontend για ολοκλήρωση στο νέο backend απορρίπτεται λόγω ελλιπών πεδίων.

## Τεχνικές λεπτομέρειες και επαναφορά

Τα elevation_gain_m και moving_minutes είναι nullable μόνο για παλιές βόλτες. Τα νέα δεδομένα ολοκλήρωσης ελέγχονται στον browser και στον server. Η RPC voltes_finish_ride αποθηκεύει βόλτα, ιδιωτικό σχόλιο και νέους επισκέπτες στην ίδια συναλλαγή. Δεύτερη ολοκλήρωση επιστρέφει 409. Η διαγραφή βόλτας διαγράφει και το ιδιωτικό σχόλιο μέσω foreign key. Τα υφιστάμενα attendees/slowed υποστηρίζονται τόσο ως JSON arrays όσο και ως SQL text arrays. Η κοινή επικύρωση υπάρχει αυτούσια σε δύο αρχεία (frontend και Function), με τεστ ισότητας για να μη διαφέρουν.

Για επαναφορά έκδοσης αποκατάστησε μαζί τον προηγούμενο κώδικα Function και frontend. Κράτησε τις νέες στήλες/πίνακα, ώστε να μη χαθούν καταχωρίσεις. Μην κάνεις DROP για απλή επαναφορά κώδικα. Οι υπάρχουσες πολιτικές RLS δεν διαγράφονται. Η migration εσκεμμένα αποκλείει απευθείας browser πρόσβαση στους πίνακες· άλλοι εξωτερικοί καταναλωτές, αν υπάρχουν, χρειάζονται ξεχωριστό έλεγχο πριν από παραγωγή.
